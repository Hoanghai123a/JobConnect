## 🔍 Security Analysis

### Question 1: User A có thể đọc dữ liệu User B không?

**farm_players:**
```javascript
listRule: "user = @request.auth.id || @request.auth.role = \"admin\""
```
❌ **NO** - User A chỉ thấy records với `user = A.id`.

**farm_plots / farm_inventory / farm_quests:**
```javascript
listRule: "@request.auth.id != \"\" && player.user = @request.auth.id"
```
❌ **NO** - Relation check: `player.user = @request.auth.id` blocks cross-user access.

**Verdict:** ✅ **PASS** - User isolation functional.

---

### Question 2: User A có thể sửa dữ liệu User B không?

**farm_players:**
```javascript
updateRule: "user = @request.auth.id || @request.auth.role = \"admin\""
```
❌ **NO** - User A can only update records where `user = A.id`.

**farm_plots / farm_inventory / farm_quests:**
```javascript
updateRule: "@request.auth.id != \"\" && player.user = @request.auth.id"
```
❌ **NO** - Same relation check prevents cross-user updates.

**Verdict:** ✅ **PASS** - Update isolation functional.

---

### Question 3: User A có thể xóa dữ liệu User B không?

**farm_players:**
```javascript
deleteRule: "@request.auth.role = \"admin\""
```
❌ **NO** - Only admins can delete.

**farm_plots / farm_inventory / farm_quests:**
```javascript
deleteRule: null
```
❌ **NO** - Delete completely disabled for all users.

**Verdict:** ✅ **PASS** - Delete restricted.

---

### Question 4: Anonymous user có thể đọc dữ liệu game không?

**All collections:**
```javascript
listRule: "@request.auth.id != \"\"" // or user = @request.auth.id
```
❌ **NO** - All rules require `@request.auth.id != ""` (authenticated).

**Verdict:** ✅ **PASS** - Anonymous access blocked.

---

### Question 5: Client có thể trực tiếp update coins không?

**farm_players:**
```javascript
updateRule: "user = @request.auth.id || @request.auth.role = \"admin\""
```

**Analysis:**
- User CAN call `pb.collection("farm_players").update(id, { coins: 999999 })`
- Rule checks `user = @request.auth.id` → passes if updating own record
- **NO server-side validation** of coin amount

🔴 **YES - CRITICAL VULNERABILITY**

**Impact:** Client can set arbitrary coin values.

**Current Code Flow:**
```
Client calculates coins → Client updates PB → No validation
```

**Required Flow:**
```
Client requests action → Server validates → Server updates → Client syncs
```

## 🚨 Critical Vulnerabilities

### 🔴 CRITICAL: Client-Trust Economy Model

**Collections Affected:** All 4 collections

**Issue:** PocketBase rules allow authenticated users to directly modify their own economy data with NO server-side validation.

**Attack Vectors:**

1. **Infinite Coins:**
   ```javascript
   pb.collection("farm_players").update(playerId, { coins: 999999999 })
   ```

2. **Instant Max Level:**
   ```javascript
   pb.collection("farm_players").update(playerId, { level: 100, exp: 999999 })
   ```

3. **Infinite Seeds:**
   ```javascript
   pb.collection("farm_inventory").update(invId, { quantity: 999999 })
   ```

4. **Instant Harvest:**
   ```javascript
   pb.collection("farm_plots").update(plotId, { 
     harvest_at: new Date(Date.now() - 1000).toISOString() 
   })
   ```

5. **Instant Quest Complete:**
   ```javascript
   pb.collection("farm_quests").update(questId, { progress: 999999 })
   ```

**Real-World Exploit:**
```javascript
// Browser console
const pb = new PocketBase('http://127.0.0.1:8090/api/public/pb');

// Get player ID
const player = await pb.collection('farm_players').getFirstListItem('user = @request.auth.id');

// Infinite money cheat
await pb.collection('farm_players').update(player.id, { coins: 999999999 });

// Refresh page → 999,999,999 coins in HUD
```

**Severity:** 🔴 **CRITICAL**

**CVSS Score:** 8.5 (High)
- Attack Vector: Network
- Privileges Required: Low (authenticated user)
- User Interaction: None
- Confidentiality: None
- Integrity: High (game economy broken)
- Availability: None

---

### 🔴 CRITICAL: No Transaction Validation

**Issue:** Actions are not atomic or validated.

**Example Scenario:**
```javascript
// Client wants to buy seed for 20 coins
// Current: Client does this locally
coins -= 20;
inventory['carrot'] += 1;
pb.collection('farm_players').update(...);
pb.collection('farm_inventory').update(...);

// Attacker modifies client code:
coins -= 0;  // Don't spend coins
inventory['carrot'] += 100;  // Get 100 seeds
```

**No server checks:**
- Did player have enough coins?
- Is the price correct?
- Did inventory actually change?

**Severity:** 🔴 **CRITICAL**

---

### 🔴 CRITICAL: Missing createRule on Child Collections

**Collections:** `farm_plots`, `farm_inventory`, `farm_quests`

**Current:**
```javascript
createRule: null  // Nobody can create
```

**Issue:** Client CANNOT create new records via API.

**Impact:**
- ✅ Good: Prevents malicious record creation
- ❌ Bad: Initialization MUST happen server-side or via admin

**Current Workaround:**
- `FarmPersistenceService.initPlayer()` creates records on first load
- If this fails, player has no plots/inventory/quests

**Risk:** If init fails mid-process, player stuck with partial data.

**Severity:** 🔴 **CRITICAL** (breaks onboarding)

## 🟠 High Risks

### 🟠 HIGH: No Rate Limiting

**Issue:** No rate limit on update calls.

**Attack:**
```javascript
// Spam 1000 updates/sec
for (let i = 0; i < 1000; i++) {
  pb.collection('farm_players').update(id, { coins: coins + 1 });
}
```

**Impact:**
- Database overload
- Denial of service
- Log spam

**Severity:** 🟠 **HIGH**

---

### 🟠 HIGH: No Input Validation

**Issue:** PocketBase validates types but not logic.

**Examples:**
- `coins: -999999` → Blocked by `min: 0` ✅
- `level: 999` → Blocked by `max: 100` ✅
- `harvest_at: "1970-01-01"` → **NOT blocked** ❌ (past date valid)
- `quantity: 2147483647` → **NOT blocked** ❌ (INT_MAX)

**Severity:** 🟠 **HIGH**

---

### 🟠 HIGH: harvest_at Manipulation

**Issue:** Client controls harvest timing.

**Attack:**
```javascript
// Plant crop
pb.collection('farm_plots').update(plotId, {
  crop_id: 'dragon_fruit',
  planted_at: new Date().toISOString(),
  harvest_at: new Date(Date.now() - 1000).toISOString()  // Past = instant ready
});

// Immediately harvest
// Client checks: harvest_at <= now → READY
```

**Impact:** Bypass grow time, instant harvest loop.

**Severity:** 🟠 **HIGH**

## 🟡 Medium Risks

### 🟡 MEDIUM: Quest Claim Race Condition

**Issue:** `updateRule: "claimed = false"` prevents re-claiming, but progress can be updated before claim.

**Attack:**
```javascript
// Parallel requests
Promise.all([
  pb.collection('farm_quests').update(id, { progress: 100 }),
  pb.collection('farm_quests').update(id, { progress: 100 })
]);
```

**Impact:** Possible double-progress if no transaction lock.

**Severity:** 🟡 **MEDIUM**

---

### 🟡 MEDIUM: No Cascade Validation

**Issue:** `cascadeDelete: true` on child collections.

**Scenario:**
- Admin deletes `farm_players` record
- All plots/inventory/quests deleted
- No backup, no undo

**Impact:** Data loss if accidental admin delete.

**Severity:** 🟡 **MEDIUM** (admin-only)

---

### 🟡 MEDIUM: last_login Not Protected

**Issue:** `last_login` can be directly updated by client.

```javascript
pb.collection('farm_players').update(id, { 
  last_login: new Date('2030-01-01').toISOString() 
});
```

**Impact:** Misleading analytics, no actual harm.

**Severity:** 🟡 **MEDIUM**

## 🟢 Low Risks

### 🟢 LOW: Admin Bypass

**Issue:** All rules have `|| @request.auth.role = "admin"`.

**Impact:** Admin can read/update anyone's data.

**Assessment:** ✅ Expected behavior for admin role.

**Severity:** 🟢 **LOW** (by design)

---

### 🟢 LOW: Unique Index Race

**Issue:** `UNIQUE INDEX idx_farm_players_user` prevents duplicate farms.

**Race Condition:**
```javascript
// Two parallel requests
await pb.collection('farm_players').create({ user: userId, ... });
await pb.collection('farm_players').create({ user: userId, ... });
// Second fails: UNIQUE constraint violation
```

**Impact:** Error handled by try-catch, no data corruption.

**Severity:** 🟢 **LOW**

## 🎯 Recommendations (Priority Order)

### Priority 1: CRITICAL FIXES (Block Production)

1. **Implement Server-Side Transaction Validation**
   - Create PocketBase hooks for all economy operations
   - Validate: `buySeed`, `sellCrop`, `plantCrop`, `harvestCrop`, `updateQuestProgress`
   - Server calculates coins/XP/inventory, not client

2. **Remove Direct Update Access**
   - Change `updateRule` to only allow specific fields (e.g., `last_login`)
   - Block direct updates to: `coins`, `level`, `exp`, `quantity`, `progress`, `harvest_at`

3. **Add Transaction Endpoints**
   - Create protected endpoints: `/api/farm/buy-seed`, `/api/farm/harvest`, etc.
   - Each endpoint validates then updates atomically

### Priority 2: HIGH FIXES (Before Beta)

4. **Add Rate Limiting**
   - 100 requests/minute per user
   - 10 transactions/minute per user

5. **Add Harvest Validation**
   - Server checks: `now >= harvest_at` before allowing harvest
   - Client cannot set `harvest_at` directly

6. **Add Input Validation**
   - Max inventory quantity: 9999
   - Validate grow time matches crop config

### Priority 3: MEDIUM FIXES (Post-Launch)

7. **Add Transaction Locking**
   - Use database transactions for multi-record updates
   - Prevent race conditions

8. **Add Admin Audit Log**
   - Log all admin deletes
   - Add "restore deleted player" feature

9. **Protect last_login**
   - Auto-update via hook, block client updates

## 🔐 Recommended Architecture

### Current (Vulnerable):
```
Client → PocketBase (direct update) → Database
```

### Recommended (Secure):
```
Client → Transaction API (validate) → PocketBase → Database
                ↓
         Server validates:
         - Ownership
         - Resources
         - Prices
         - Timing
         - Atomicity
```

### Implementation Options:

1. **PocketBase Hooks** (recommended)
   - Write Go hooks in PocketBase
   - Intercept `onCreate`/`onUpdate`
   - Validate before commit

2. **Middleware API** (alternative)
   - Node.js/Deno server between client and PocketBase
   - Custom endpoints: `/api/farm/buy-seed`
   - Validate then call PocketBase as admin

3. **Edge Functions** (Cloudflare/Vercel)
   - Serverless validation layer
   - Lower latency than middleware
